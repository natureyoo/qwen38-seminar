    Two loops, one harness

    Training-time RL loop와 Inference-time agent loop

    A · Training-time agentic RL loop

    Task/workspace sampler→ Harness/env constructor→ Policy→ Tool action ⇄ Env→ Trajectory→ Verifier / rubric judge→ Reward→ RL learner → weight update

    B · Inference-time agent loop

    User task→ Harness→ Model→ Tool action ⇄ Env→ Test / verifier→ retry 또는 완료

    이 loop에서는 일반적으로 model weight가 업데이트되지 않는다.

    loop 구조: Qwen3.8 blog 서술 기반 발표자 재구성04

    2분. 두 loop의 앞부분은 동형(model→tool→env→verifier)이고, 차이는 꼬리(reward→learner→weight update)에만 있다는 점을 강조. 그래서 같은 harness를 양쪽에 재사용할 수 있고, 그것이 Qwen 전략의 핵심.

    용어 주의(질문 대비): Qwen 원문의 "self-evolution"·"continuous learning"은 사례별로 (a) context 안에서 다음 action을 바꾸는 in-context adaptation(칩 500-turn, E-commerce 2,000 rounds), 또는 (b) code·workflow 같은 외부 artifact 수정(oh-my-cli)을 가리킨다. 실행 중 weight update는 어느 사례에도 없다 — weight가 바뀌는 것은 training pipeline의 learner뿐.

    Reward & data engine

    이종 task에 reward를 주는 방법, 그리고 batch를 지키는 방법

    Universal reward system

    • Execution-based checking — test·실행 결과
    • Rubric-conditioned adjudication — text 및 rendered visual output 평가
    • Agentic inspection — trajectory 자체를 검사
    • "automatically scalable rubrics" 아래 하나의 reward system으로 통합 — task-specific verifier 유지보수의 비일관성 제거가 명시된 동기

    난점: normalization · sparsity · judge bias · correlated error · reward hacking. aggregation formula 미공개 — 수식을 지어내지 않는다. reward hacking 인지의 공식 증거: NL2Repo 각주 "To prevent reward hacking, we disable Bash commands … such as pip download, pip install, and git clone"

    Online data balancer

    "shapes every batch to keep its distribution over tasks, difficulty, workspaces, and harnesses highly balanced, suppressing inter-batch gradient variance"
    • 쉬운 task의 batch 독점, 긴 task의 compute 독점 방지
    • 성공률 ~0%/~100% task의 학습 신호 소실 관리
    • 환경별 reward scale 차이 → inter-batch gradient variance 억제가 명시 목적

    balancing 축 4개(harness 포함)는 원문에 명시됨. 단 축별 목표 분포·비율은 미공개. 실패 trajectory 활용·off-policy 재사용 여부도 미공개.

    Qwen3.8 blog — reward & data sections, 2026-08-07 열람 · 상세 논점 → Appendix C07

    Multimodality at the harness layer

    Qwen-MM-Plugins — model 내장 기능이 아니라 harness 확장 레이어

    "a harness extension library designed for multimodal agents … any existing agent harness can be extended into a more naturally multimodal-native system." — Qwen3.8 blog

    Assessment

    부가 기능인가, 멀티모달 agent의 공통 레이어가 될 것인가

    의미가 클 수 있는 이유

    • Multimodality를 model API가 아니라 harness layer로 — visual observation이 planning·execution·inspection·retry에 연결
    • observation뿐 아니라 action까지: see → act → render → inspect → revise
    • skill+MCP 패키징으로 harness portability 시도
    • 100시간 영상을 context 대신 외부 graph memory로
    • CAD/3D 전문 앱을 agent action space로 노출
    • 환경 확장 축에 modality×tool capability 추가 가능성

    아직 검증되지 않은 것

    • 실제 third-party adoption · 장기 유지보수
    • Qwen/DashScope 종속성 · 타 model에서의 성능
    • visual feedback 정확도 · long-video retrieval 품질
    • CAD 결과의 semantic correctness 평가
    • GUI app 실행 실패 복구 · permission/security
    • 대용량 media 비용·latency · production use
    repo stats(별점·기여자 등)는 sources 페이지에 조회 날짜와 함께 기록16

    1.5분. "이미 표준이 됐다"고 말하지 않기. 좌우 균형이 이 슬라이드의 메시지 그 자체.

    구두 평가: 아키텍처적 영향 가능성은 크다 — 멀티모달 능력을 특정 UI나 model endpoint에 가두지 않고 portable harness capability로 패키징하기 때문. 다만 프로젝트가 새로워 생태계 채택과 production 안정성은 검증 단계 (GitHub stars ≠ 기술적 영향력).

    Related work — 반대 방향에서 온 같은 결론

    LongHorizon-Harness: model은 그대로, state·verification을 harness로

    Qwen을 만드는 Alibaba의 다른 팀(AMAP-ML · DreamX Team)이 2026-08-03 공개한 논문·프레임워크 — 나흘 만에 330 stars. Qwen3.8이 model을 environment에 맞춰 RL 학습시키는 접근이라면, 이쪽은 model weight를 건드리지 않고 long-horizon 실행을 세 역할로 분해한 harness다 — Manage–Execute–Audit loop.

    Manager

    원래 목표·검증된 진행 상태·다음 단계를 유지하고 subtask를 선택

    Executor — 매 라운드 fresh context

    누적된 오류·긴 이력 없이, 명확히 정의된 task 하나만 수행

    Auditor — 읽기 전용 독립 검증

    파일·인터페이스·로그·테스트를 실제 환경에서 검사 — 검증을 통과한 결과만 persistent task state에 기록

    같은 model, harness만 교체했을 때

    BenchmarkModel기본 harnessMEA
    WeaveBench (114)Qwen3.7-Plus51.8 (Claude Code)80.7
    Opus 4.741.2 (Claude Code) · 35.1 (OpenClaw)—
    Terminal-Bench 2.1Qwen3.7-Plus69.777.2

    논문·프로젝트 페이지 자체 평가 수치. backend-agnostic — Claude Code·Codex를 AgentAdapter로 장착

    WeaveBench에서 Qwen3.7-Plus + MEA(80.7)가 Opus 4.7 + Claude Code(41.2)를 역전 — harness 설계가 model 격차를 뒤집은 사례. Auditor는 곧 inference-time verifier다.

    github.com/AMAP-ML/LongHorizon-Harness (MIT, 330 stars) · arXiv 2608.01964 "LongHorizon-Harness: Advancing Long-Horizon Agents for Real-World Tasks" (Ma et al., 2026-08-03) · 2026-08-07 열람17

    1분. 위치가 중요: Qwen3.8과 "다른" 프로젝트지만 결론이 같다 — long-horizon capability는 시스템 속성이라는 것. Qwen은 training(RL environment) 쪽에서, 이쪽은 inference harness 쪽에서 같은 지점에 도달.

    구두 포인트: "executor를 매번 fresh하게"가 핵심 설계 — 긴 context에 오류가 누적되는 대신, 상태는 Manager의 검증된 task state 파일에만 산다. oh-my-cli의 lease·상태 기계와 정확히 같은 문제의식. Auditor가 검증한 것만 상태에 들어간다는 규칙은 universal reward system의 inference-time 버전.

    수치 주의: 논문 자체 평가이며(독립 재현 미확인), OSWorld 2.0은 절대값이 낮은(2.8→8.3%) 어려운 벤치마크라 배율이 커 보이는 것. Opus 4.7 OSWorld 수치는 출처 간 표기가 갈림 — abstract는 subset 기준 20.0→34.3, 프로젝트 페이지 표는 13.9→35.3(binary)·49.1→66.9(partial). 슬라이드에는 프로젝트 페이지 표를 실었고, 질문이 오면 "subset·metric 정의 차이"로 설명.

    1분. 이 슬라이드의 힘: 논문 수치는 자체 평가지만, 이 화면은 발표자가 직접 재현한 것 — 설치부터 실행까지 명령 한 줄이었다는 점.

    구두 연결: 대시보드의 audit 판정 문구가 앞 슬라이드의 "검증 통과한 것만 상태에 기록"의 실물. oh-my-cli(사례 1)의 lease·CI와 같은 문제의식이 다른 팀의 다른 구현으로 또 나타난다 — long-horizon의 공통 인프라 패턴이 수렴하고 있다는 신호.

    데모 링크를 열어 보여줄 때(선택): 앱은 Node 서버라 Pages에서 그대로 못 돌리므로 API 응답을 정적 JSON으로 스냅샷했고, fetch를 가로채는 shim이 응답한다 — 프론트엔드 코드는 원본 그대로다. 정렬·필터·상세 뷰 모두 동작하며 재수집만 안 된다.

    정직한 후일담(A/B 결과는 구두로): 같은 task를 harness 없이 Sonnet 5 단독으로도 시켜봤는데 결과물이 비슷했다. output 토큰은 MEA가 3.6배(721K vs 203K). 이 크기의 task에서는 harness 이득이 안 나온다는 뜻 — 논문이 개선을 보인 벤치마크가 전부 long-horizon인 이유. 더 중요한 건, 15라운드 audit이 통과시킨 앱의 실제 결함이 "랭킹이 유용하지 않다"였고 그건 rubric에 없어서 아무도 못 잡았다는 점. 발표자가 제품을 열어보고 5분 만에 진단했고(회사 블로그만 수집 + 검증 규칙이 독립 2소스 요구 → 구조적 모순, fixture가 실데이터를 밀어냄), 고치는 데는 어댑터 2개였다. verifier가 커버하지 않는 품질 축은 loop를 아무리 돌려도 올라가지 않는다.

    Conclusion

    1 · Long-horizon capability는 model이 아니라 시스템의 속성이다
    Model × Harness × Environment × Verifier × State × Budget

    2 · Agentic RL의 핵심 자산은 학습 가능한 업무 환경이다
    executable workspace · toolchain · verifier · reset 가능성

    3 · 칩 설계는 검증 가능한 폐루프라 적합한 domain이다
    단, 공개 45nm flow와 production tape-out의 간극은 크다

    현실 업무를 rollout 가능하고 reward 가능한 environment로 바꾸는 것 —
    그것이 자율 실행 시간을 며칠 단위로 늘린 방법이다.
