    What actually changed

    아키텍처는 Qwen3.5 그대로 — 바뀐 것은 RL environment다

    Model architecture — 새것 없음

    • "Built upon the architectural foundation of Qwen 3.5" 공식
    • 2.4T params (95B active)로 scale
    • 새 아키텍처 요소 발표 없음 · tech report 없음

    Post-training — RL environment 다양화

    • Task × Workspace × Harness 조합 확장
    • universal reward · 4축 online balancer
    • 학습 환경 = Claude Code·Codex 등 실제 inference harness 그 자체

    발표 방식 — 극한 use case 시연

    • 16일 자율 소프트웨어 운영 (oh-my-cli)
    • 125시간 논문 재현·개선
    • 500-turn 칩 설계
    이 RL 학습의 목적은 결국 inference-time harness를 잘 쓰는 모델을 만드는 것이다. Qwen3.8의 새로움은 model architecture가 아니라, 얼마나 다양한 environment에서 RL을 돌렸는가와 그 결과를 얼마나 긴 자율 실행으로 보여주는가에 있다.
    "Built upon the architectural foundation of Qwen 3.5, Qwen 3.8-Max scales to 2.4 trillion parameters" — Qwen3.8 blog03

    2분. 발표 전체의 프레임을 여기서 세운다: 이번 릴리스에서 모델 쪽의 새로움은 없다(공식적으로 Qwen3.5 아키텍처 기반, 신규 아키텍처 발표 없음). 새로움은 post-training의 RL environment 다양화이고, 그 목적은 inference-time harness 사용 능력이다.

    포인트: 학습에 쓰인 harness(Claude Code, Codex 등)가 곧 사용자가 실제로 쓰는 harness다 — training environment와 inference environment가 같은 물건이라는 것이 이 접근의 핵심. 이후 슬라이드(4: 두 loop, 5–7: environment 확장 방법, 9–13: 극한 use case)가 이 세 칸을 각각 전개한다.

    Two loops, one harness

    Training-time RL loop와 Inference-time agent loop

    A · Training-time agentic RL loop

    Task/workspace sampler→ Harness/env constructor→ Policy→ Tool action ⇄ Env→ Trajectory→ Verifier / rubric judge→ Reward→ RL learner → weight update

    B · Inference-time agent loop

    User task→ Harness→ Model→ Tool action ⇄ Env→ Test / verifier→ retry 또는 완료

    이 loop에서는 일반적으로 model weight가 업데이트되지 않는다.

    "한 번의 500-turn trajectory 안에서 결과가 좋아졌다"는 것은 closed-loop in-context adaptation을 보여준다. 그 자체로 실행 중 model weight가 온라인 업데이트됐다는 뜻은 아니다.
    loop 구조: Qwen3.8 blog 서술 기반 발표자 재구성04

    2분. 두 loop의 앞부분은 동형(model→tool→env→verifier)이고, 차이는 꼬리(reward→learner→weight update)에만 있다는 점을 강조. 그래서 같은 harness를 양쪽에 재사용할 수 있고, 그것이 Qwen 전략의 핵심.

    용어 주의(질문 대비): Qwen 원문의 "self-evolution"·"continuous learning"은 사례별로 (a) context 안에서 다음 action을 바꾸는 in-context adaptation(칩 500-turn, E-commerce 2,000 rounds), 또는 (b) code·workflow 같은 외부 artifact 수정(oh-my-cli)을 가리킨다. 실행 중 weight update는 어느 사례에도 없다 — weight가 바뀌는 것은 training pipeline의 learner뿐.

    Scope of the claim

    Multi-harness RL — 주장하는 것과 주장하지 않는 것

    Qwen이 주장하는 것 공식

    • "jointly scaling RL environments and compute" → "general working competence"를 QwenWork · Claude Code · Codex · OpenClaw · Hermes에서 "uniformly" 향상
    • Task/Workspace/Harness 독립 축 — 환경마다 개별 구축 없이 조합으로 확장 ("compounds combinatorially")

    공식 자료로 확인 안 되는 것 미공개

    • 전체 task × workspace × harness 조합의 학습 matrix
    • harness별 sampling 비율 · trajectory 수
    • Figure의 harness들이 전부 training set에 포함됐는지
    • 공개 사례 harness와 RL training harness의 config 동일성
    • RL algorithm · rollout 수
    가장 정확한 요약: "task·workspace·harness를 분리 가능한 축으로 만들고 다양한 조합에서 rollout을 생성하는 방향으로 확장했다고 주장한다. 전수 학습 matrix와 비율은 공개하지 않았다." — 여러 harness에서 성능이 비슷하다는 결과는 harness-invariant policy의 증거일 수도, 비슷한 affordance를 가진 scaffold에서 평가됐다는 뜻일 수도 있다.

    Reward & data engine

    이종 task에 reward를 주는 방법, 그리고 batch를 지키는 방법

    Universal reward system 공식

    • Execution-based checking — test·실행 결과
    • Rubric-conditioned adjudication — text 및 rendered visual output 평가
    • Agentic inspection — trajectory 자체를 검사
    • "automatically scalable rubrics" 아래 하나의 reward system으로 통합 — task-specific verifier 유지보수의 비일관성 제거가 명시된 동기

    난점: normalization · sparsity · judge bias · correlated error · reward hacking. aggregation formula 미공개 — 수식을 지어내지 않는다. reward hacking 인지의 공식 증거: NL2Repo 각주 "To prevent reward hacking, we disable Bash commands … such as pip download, pip install, and git clone" 공식

    Online data balancer 공식

    "shapes every batch to keep its distribution over tasks, difficulty, workspaces, and harnesses highly balanced, suppressing inter-batch gradient variance"
    • 쉬운 task의 batch 독점, 긴 task의 compute 독점 방지
    • 성공률 ~0%/~100% task의 학습 신호 소실 관리
    • 환경별 reward scale 차이 → inter-batch gradient variance 억제가 명시 목적

    balancing 축 4개(harness 포함)는 원문에 명시됨. 단 축별 목표 분포·비율은 미공개. 실패 trajectory 활용·off-policy 재사용 여부도 미공개.

    설계 단계 중 어디까지 갔나

    RTL → simulation → synthesis → floorplan → placement → CTS → routing → STA/timing closure ✓ 여기까지
    ✗ sign-off → tape-out → fabrication → packaging/test

    Nangate45는 공개 연구·교육용 45nm 라이브러리 — 최신 production 공정이 아니다. 이 결과는 physical-layout 구현이지 제조된 silicon이 아니며, production-ready IP로 확대 해석할 수 없다. 원문의 "physical feasibility fully guaranteed by OpenROAD backend validation"은 실제 sign-off(DRC/LVS/정밀 STA)·fabrication 관점에서 과한 표현이다.

    Multimodality at the harness layer

    Qwen-MM-Plugins — model 내장 기능이 아니라 harness 확장 레이어

    Assessment

    부가 기능인가, 멀티모달 agent의 공통 레이어가 될 것인가

    의미가 클 수 있는 이유

    • Multimodality를 model API가 아니라 harness layer로 — visual observation이 planning·execution·inspection·retry에 연결
    • observation뿐 아니라 action까지: see → act → render → inspect → revise
    • skill+MCP 패키징으로 harness portability 시도
    • 100시간 영상을 context 대신 외부 graph memory로
    • CAD/3D 전문 앱을 agent action space로 노출
    • 환경 확장 축에 modality×tool capability 추가 가능성

    아직 검증되지 않은 것 미검증

    • 실제 third-party adoption · 장기 유지보수
    • Qwen/DashScope 종속성 · 타 model에서의 성능
    • visual feedback 정확도 · long-video retrieval 품질
    • CAD 결과의 semantic correctness 평가
    • GUI app 실행 실패 복구 · permission/security
    • 대용량 media 비용·latency · production use
    아키텍처적 영향 가능성은 크다 — 멀티모달 능력을 특정 UI나 model endpoint에 가두지 않고 portable harness capability로 패키징하기 때문이다. 다만 프로젝트가 새로워 생태계 채택과 production 안정성은 아직 검증 단계다. (GitHub stars ≠ 기술적 영향력)

    Conclusion

    1 · Long-horizon capability는 model 단독 속성이 아니다 —
    Model × Harness reliability × Environment quality × Verifier coverage × State management × Compute budget
    2 · Agentic RL의 핵심 자산은 task text가 아니라 학습 가능한 업무 환경이다 — executable workspace · toolchain · verifier · reset · failure trajectory.
    3 · 칩 설계는 검증 가능한 폐루프 덕에 적합한 domain이지만, open-source 45nm flow와 production tape-out 사이의 간극은 크다.

    Qwen3.8 발표에서 가장 중요한 것은 또 하나의 더 큰 모델이 아니라, 현실 업무를 rollout 가능하고 reward 가능한 environment로 바꾸면 agent의 자율 수행 범위를 며칠 단위까지 확장할 수 있다는 시스템적 가설이다. Qwen-MM-Plugins는 같은 방향을 multimodal domain으로 확장한다 — 보고, 행동하고, 결과를 다시 검증하는 harness를 만들려는 시도다.
